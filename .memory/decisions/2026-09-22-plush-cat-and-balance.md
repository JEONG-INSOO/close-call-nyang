# Decisions: 인형형 냥대리와 빠른 균형 조작감

- Date: 2026-09-22
- Status: Confirmed
- Source: 사용자 실플레이 피드백과 첨부 인형 사진; 후속 선택 `1` (빠른 흔들림·빠른 조작·약65도 실패)
- Stage: 인터뷰 완료. 구현·새 빌드·배포·실플레이 검증은 아직 수행하지 않았다.
- Supersedes: 기존 캐릭터의 긴 바지 다리/구두 실루엣, 약1.74등신 고정 비율 및 criticalAngleRad=0.7의 초기 튜닝. 다른 기획은 유지한다.

## D01. 세 캐릭터 공통 인형형 실루엣

- **Chosen (사용자 요청)**: 사람 같은 길쭉한 다리 대신 짧고 둥근 고양이 발, 몸에 가까운 짧은 팔, 통통하고 둥근 몸으로 변경한다. 두 발로 종종 걷는 냥대리는 유지한다.
- **Rationale**: 첨부 사진에서 원하는 것은 짧은 팔다리와 포근한 체형이다. 긴 바지와 구두가 현재의 사람 같은 인상을 만들고 있다.
- 세 캐릭터 rookie/diligent/veteran 모두 같은 새 체형과 팔다리·커피 잡는 위치를 공유한다. 기존 표정 차이·직장인 의상(셔츠/재킷/넥타이/사원증)과 크림색 털/기본 색 체계를 유지한다.
- 사진의 분홍색 몸·얼굴·귀·무늬 등을 그대로 재현하는 작업이 아니다. 현재의 독창적인 SVG 캐릭터 체계를 직접 수정하며 새 비트맵 이미지나 외부 캐릭터 자산은 도입하지 않는다.
- 구체적인 리그 좌표/높이·발 들기 폭은 계획에서 명시한다. 현재 전체205/머리118/몸통51/다리36이라는 수치에 새 디자인을 억지로 맞추지 않는다. 발밑 기준점, 커피 접점, 지면 접촉·기울기 가독성을 함께 검증한다.

## D02. 빠르고 아슬아슬한 균형 감각

- **Chosen (사용자 선택1)**: 초반부터 기울어지는 움직임과 좌우 조작 반응을 빠르게 하고, 크게 휘청거려도 반대쪽 조작으로 회복하는 재미를 목표로 한다.
- **Chosen (사용자 선택1)**: 실패 각도는 수직 기준 좌우 약65도를 첫 튜닝 기준으로 한다. 약40도였던 현재보다 충분히 기울어진 뒤 실패하도록 한다.
- **Rationale**: 사용자는 현재 기울어짐이 느리고 작은 기울기에서 끝나는 느낌을 보고했다. 단순히 허용각만 넓히면 느린 움직임은 그대로이므로 입력 힘·불안정성·감쇠를 함께 조정해야 한다.
- 65도는 최초 테스트 기준이지 이미 최적화된 수치라는 주장이 아니다. 구현 단계에서 기존/변경 후 동일 조건을 비교하고 실제 웹 플레이로 화면상 기울기·반응을 검증한다. 임의의 속도 배수나 미실행 테스트 결과를 확정값으로 쓰지 않는다.
- 더 큰 각도에서도 화면 회전과 실제 판정이 일치해야 한다. 화면만 과장해서 기존40도 판정을 감추지 않는다. 별도 실패 유예시간, 자동 중앙 복귀, 새 조작 방식, 난이도 선택 메뉴, 지면 충돌 시뮬레이션은 추가하지 않는다.

## D03. 유지되는 게임 규칙과 저장 데이터

- **Chosen (기존 요구 유지)**: 좌우 버튼/키 조작, 동시 좌우 입력=0, 균형 게이지 없음, 가로 횡스크롤을 유지한다.
- **Chosen (기존 요구 유지)**: 15% 커피/가속, 51% 사무실, 거리1m=성공률1%, 100% 이후 계속 진행을 유지한다. 걷는 거리 속도 공식은 변경하지 않아 중단 없이100%까지 약90초인 기존 목표를 유지한다. 기울기 속도와 전진 속도를 혼동하지 않는다.
- **Chosen (기존 요구 유지)**: 기본2번, 100% 첫 달성1번, 서로 다른10판 달성3번을 유지한다. 외형별 물리·판정 차이는 만들지 않는다.
- 기존 로컬 최고점/해금/설정·닉네임/세션을 초기화하지 않는다. 캐릭터ID·앱 기술 식별자·저장 키는 유지한다. 이 변경으로 과거 해금을 취소하거나 점수를 삭제하지 않는다.

## D04. 코드에서 확인한 구현 제약

- **Confirmed from code**: `src/game/balance.ts`는 criticalAngleRad0.7(약40.1도), controlAcceleration4.8, damping3.2, fixedDt1/120이다. `engine.ts`는 각속도를 갱신한 뒤 각도를 적분하고 임계값에서 즉시 실패시킨다. 초기 기울기는±0.025rad이고 각속도는0이다.
- **Confirmed from code**: `src/scene/NyangCharacter.tsx`는 실패 전 angleRad를 그대로 회전으로 표시한다. 다리는36단위의 바지/구두 그림이고 모든 캐릭터가 동일 리그를 쓴다. 실패 후82도까지 마무리하는 표시 애니메이션은 점수/물리 상태를 바꾸지 않는다.
- **Confirmed from code**: 물리 원본 파일의 해시로 RULES_VERSION을 생성하고 서버 사본을 동기화한다. 물리 변경 시 앱만 고치면 서버 재생 검증이 달라지므로 `ranked:sync`와 Node/Deno/브라우저 골든 재검증이 필요하다. Hermes는 별도 실기기 검증이며 자동 통과로 기록하지 않는다.
- 고정 틱/결정적 난수/1e-9 수치 정규화, 임계각 경계·보호·동시입력 처리를 유지한다. 임계각을 바꾸면 관련 테스트의0.69/0.7 하드코딩과 wobble/보호 상대각도도 함께 검토한다. 실패하는 골든 값을 근거 없이 덮어쓰지 않는다.

## D05. 기존 서버 작업과 순서

- **Execution boundary**: 사용자 요청의 외형·조작감 변경을 다음 계획 대상으로 우선한다. 현재 P02-T03은 완료 처리하지 않고 재개할 경로와 실제 Supabase 검증 증거를 보존한다.
- 이번 단계는 결정 문서화만 한다. 다음 `memory-plan`에서 새 변경의 단일 Phase/순차 Task와 기존 T03 복귀 지점을 만든다. 계획 준비 전에 기존 포인터를 다른 구현 Task로 덮어쓰지 않는다.
- 현재 staging은 구 규칙으로 배포되어 있다. 새 물리 구현 후 필요한 staging 검증은 계획에 구분하고, 기존14개 smoke 통과를 새 규칙 통과로 재사용하지 않는다. production 배포·과금·추가 프로젝트 생성·GitHub 푸시는 이 선택에 포함되지 않는다.

## 요청밖이지만 알아야 할 인접 사항 (자동 구현하지 않음)

- 온라인 최고점/순위는 이미 rulesVersion별로 분리된다. 새 규칙을 도입하면 옛 점수는 DB에 보존되지만 새 순위표에 자동 합산되지 않는다. 기존 버전 입력 대기열도 새 규칙으로 재생할 수 없으며 기존 명시적 폐기/불일치 처리를 유지한다. 새 시즌 UI나 기록 이관·삭제 기능은 요청 범위 밖이다.
- 로컬 최고점은 규칙 버전별이 아니며 현재 값을 보존한다. 로컬 기록의 시즌 분리를 새로 만들지는 않는다.
- 앞선 전체 Jest에서 캐릭터 커피 opacity 검사1건이 간헐 실패 후 단독/전체 재실행 통과한 이력이 있다. 원인은 아직 확정되지 않았으므로 외형 변경 QA에서 재확인하고 테스트 통과만으로 시각 품질을 단정하지 않는다.

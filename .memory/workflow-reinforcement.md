# Memory Workflow 보강 규칙

이 프로젝트의 최종 목표는 게임을 완성하는 것과 동시에, 구현 과정을 학습노트로 남겨 개발 실력을 키우는 것이다.

## 1. 세 스킬의 역할

- `grill-me`: 요구사항과 설계 결정을 한 번에 하나씩 확정한다.
- `memory-plan`: 구현 전에 독립적으로 실행 가능한 청사진을 만든다. 이 단계에서는 소스 코드를 수정하지 않는다.
- `memory-execute`: 현재 포인터가 가리키는 Task 하나만 구현하고 검증한 뒤 커밋·상태 갱신·학습 기록을 남긴다.

## 2. 상태 규칙

모든 Plan, Phase, Task는 `pending | in_progress | blocked | done` 중 하나의 상태만 사용한다. 상태는 본문 한 곳과 대시보드 한 곳에만 기록하고 서로 일치시킨다.

`current.md`는 현재 포인터만 보관한다. 과거 실행 로그는 별도 기록으로 이동하며, 완료된 Task가 Active Task로 남아 있으면 실행을 중단하고 포인터를 먼저 정리한다.

## 3. Task 청사진 필수 항목

각 Task에는 수정 파일과 심볼, 타입·스키마, 상태 전이와 오류 처리, 완료 조건, 정확한 검증 명령, 커밋 메시지, 생성 파일 재생성 절차를 적는다. 생성된 Supabase 복사본·웹 번들·리플레이 fixture는 원본 규칙 변경 후 반드시 동기화한다.

## 4. 안전한 변경과 커밋

기존 작업 트리 변경은 보존한다. Task에 포함된 파일과 해당 Task의 메모리 문서만 스테이징하며, 커밋과 원격 push는 별개의 작업으로 취급한다. push는 사용자가 명시적으로 요청한 경우에만 한다.

## 5. 차단 처리

코드 결함과 외부 환경 문제를 구분한다. 같은 외부 차단이 반복되면 Task를 `blocked`로 기록하고 원인, 재현 단계, 필요한 사용자 조치를 적는다. 테스트를 실행하지 못한 경우 성공으로 보고하지 않는다.

## 6. 학습노트 의무

각 완료 Task마다 `docs/learning-notes.md`에 초보자도 이해할 수 있게 다음을 기록한다.

1. 무엇을 만들거나 바꿨는가
2. 왜 그렇게 설계했는가
3. 핵심 코드 개념과 데이터 흐름은 무엇인가
4. 어떤 테스트로 확인했는가
5. 실패·디버깅 과정에서 배운 점은 무엇인가
6. 다음에 스스로 해볼 작은 연습은 무엇인가

사용자 선택으로 정한 결정과 코드베이스를 조사해 확인한 사실을 구분해 기록한다. 범위를 벗어난 발견은 구현하지 않고 `Out of scope`로 남긴다.

## 7. 날짜와 재현성

파일명 날짜는 프로젝트 기준 시간대(Asia/Seoul)로 생성한다. 검증 명령은 복사해 다시 실행할 수 있는 형태로 적고, 규칙 해시·fixture·빌드 산출물의 버전을 함께 기록한다.

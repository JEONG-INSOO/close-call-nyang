# 결과·홈 화면 간소화: 버튼을 지워도 기능은 남는다

결과 카드의 첫 행동을 민트색 ‘다시 도전’, 둘째를 ‘처음으로’로 고정했다. 개발용 가상 광고가 실제로 사용 가능한 경우에만 ‘광고 보고 일어서기’를 셋째 행에 둔다. 랭킹 상태·재시도·랭킹·닉네임·기록 공유·캐릭터·설정 버튼은 결과 화면에서 없앴지만, 점수·최고 기록·새 캐릭터 해금 공지는 남겼다.

중요한 경계는 **화면 진입점과 내부 처리의 분리**다. `ResultScreen`은 더 이상 랭킹 제출 상태를 받지 않지만 `App`의 `useRankedGame`은 기록을 계속 제출한다. 제출이 보류되면 다음 도전을 시작할 때 기존 `PendingRankingPanel`이 선택지를 보여준다. 광고 부활 역시 기존 `REQUEST_AD` 전이를 그대로 쓴다.

```tsx
<Pressable testID="retry-button" style={[styles.button, styles.retry]} />
<Pressable testID="result-home" style={styles.button} />
{canRevive && <Pressable testID="revive-button" style={styles.button} />}
```

홈에서는 랭킹·캐릭터·설정만 보인다. 처음 안내에서 ‘나중에’를 고른 사용자는 설정에서 닉네임을 처음 등록한다. 프로필이 존재하면 설정에 이름만 읽기 전용으로 남고 변경 버튼은 없다. `loading`은 ‘미설정’이 아니다. 서버 조회 중에 설정 버튼이 잠깐 나타나면 잘못된 두 번째 등록 화면으로 들어갈 수 있어 앱에서도 상태를 확인한다. 서버 API는 여전히 변경을 허용하므로 이번 ‘변경 불가’는 앱 UI 정책이지 서버의 불변 보장은 아니다. 온라인 정보 삭제는 개인정보 처리 경로라 유지한다.

검증 중 오래된 테스트가 삭제된 공유·결과 캐릭터 버튼을 기대해 실패했다. 새 흐름(결과 → 홈 → 캐릭터, 첫 설정은 설정 화면)을 검사하도록 수정했다. 또 `output/`의 이전 EAS 아카이브가 TypeScript와 Jest의 중복 소스로 잡혀, 실제 앱 소스 검사에서 제외했다. Jest 49스위트/691개, 타입 검사, `ranked:check`, 격리된 웹 export·fixture export, Playwright 가로 화면 6개가 통과했다. 실제 iPhone/새 TestFlight 설치 검사는 아직 하지 않았다. 이전 1.0.0(5) 제출본에는 이번 UI 변경이 없다.

복습 질문: 결과 화면에서 랭킹 문구를 없애도 기록 제출이 계속되는 이유는? 프로필 `loading`과 진짜 미등록 `guest`를 왜 구별해야 하나? 앱 버튼만 숨기고 서버 API를 그대로 두면 ‘변경 불가’는 어디까지 보장되나?
